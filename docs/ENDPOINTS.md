# Эндпоинты Lane: параметры и что именно подписывается

Документ собран **офлайн** — из дампов в `http-request-dumps/`. Запросов к
`ru.laneapi.com` при этом не делалось: токены из дампов расшифровываются ключом
из библиотеки, и по ним видно, какие ровно данные подписывало приложение.

Инструмент проверки: `python tools/dumpcheck.py [dump.txt ...]` — расшифровывает
`x-core-token`, печатает поля и пересчитывает HMAC по URL из дампа.

---

## 1. Как устроена проверка

Внутри `x-core-token` лежит `hex(HMAC) | ts | nonce | boot_id | inode | flag`.
Если пересчитать HMAC по `method:path:query:ts:nonce:field:boot_id:inode` и он
совпал — значит приложение подписывало ровно эти `method/path/query` (и пустое
тело, раз `field` пуст). Именно так проверены все строки ниже.

---

## 2. Подтверждённые эндпоинты

| Эндпоинт | Метод | Query, который подписан | Параметры | HMAC |
|---|---|---|---|---|
| `/events` | GET | `""` | — (доп. заголовки `x-connection-quality`, `x-is-vpn`) | ✅ |
| `/user/playlists` | GET | `""` | — | ✅ |
| `/user/artists` | GET | `""` | — | ✅ |
| `/user/albums` | GET | `""` | — | ✅ |
| `/user/search/history` | GET | `""` | — | ✅ |
| `/user/recent` | GET | `""` | — | ✅ |
| `/user/tracks` | POST | `prefetch=0` | тело `{"trackIds":[…]}` (шифруется) | ✅ |
| `/playlist/{id}` | GET | `""` | — | ✅ |
| `/playlist/{id}/tracks` | GET | `page=1&pageSize=50` | `page`, `pageSize` | ✅ |
| `/platforms/v2/hints` | GET | `q=…` | `q` | ⚠️ не сходится (см. §4) |

Все GET-запросы в дампах — без тела, `flag = 0`. Единственный POST
(`/user/tracks`) — с телом, `flag = 1` (см. §4.1).

Важно: подписывается **строка ровно в том виде, в каком она уходит в URL**.
Для `/playlist/lane_likes/tracks` это `page=1&pageSize=50` — то же, что в
URL. Никакой нормализации (сортировки параметров, перекодирования) для этого
эндпоинта не видно.

## 4. Аномалия `/platforms/v2/hints`
Токен расшифровывается нормально, но HMAC не сходится ни с одним из вариантов
`query`:

- `q=%D0%B7%D0%B0%D0%BF%D1%80%D0%BE%D1%81` (как в URL);
- `q=запрос` (URL-decoded);
- только значение, с `?`, в нижнем регистре, двойное кодирование;
- `path` вместе с query в одном поле и пустой `query`;
- `field` = пусто / `{}` / `null`.

Значит для этого эндпоинта подписываются какие-то другие входные данные —
например, непустое тело или дополнительные параметры, которых нет в строке
запроса. Пока не восстановлено; если снимете дамп с известным `q`, можно
подобрать перебором через `tools/dumpcheck.py`.

## 4.1. POST и тело запроса: `/user/tracks`

Единственный пока POST-эндпоинт:

```
POST /user/tracks?prefetch=0
content-type: application/json; charset=UTF8
```

**Тело шифруется.** На проводе лежит `RC4*(KEY‖nonce‖ts, plaintext_json)`, и
`msg1.field` — это ровно те же байты. Поэтому:

- подпись считается по сырым байтам тела (серверу не надо ничего расшифровывать);
- `body` в `build()` — **открытый текст**, а отправлять надо `out.payload`
  (4-й элемент, который возвращает `cdrl`);
- для GET тело пустое, поэтому там всё тривиально.

Проверено вживую: тело `{"trackIds":["2lEbe9evbwJ1unoQAb0uPk"]}` → **200** и
массив `Track`. `prefetch` можно и в query, и в теле.

Другие формы (`[...]`, `{"ids":[…]}`, `{"songIds":[…]}`, `{"tracks":[…]}`) дают
`400 INVALID_TRACK_IDS_BODY`. То есть ожидается объект именно с полем `trackIds`.

Почему в дампе тело выглядело мусором: это был шифртекст, а не JSON.

## 4.2. Воспроизведение: `/track/stream`

Главное, чего не хватало для «хэндла на проигрывание». Из APK (1.4.7,
`com.skiy.lane.data.remote.api.TracksApi`):

```java
@GET("/track/stream")
Object i(@Query("trackId") String, @Query("refId") String,
         @Query("streamQuality") String, Continuation<TrackStreamingResult>);
```

Ответ — `TrackStreamingResult`:

| Поле | Тип | Смысл |
|---|---|---|
| `url` | string | **играбельная ссылка** |
| `trackId` | string | `songId` |
| `playbackToken` | string? | опционально, по умолчанию пусто |
| `ttl` | long | срок жизни ссылки, мс (в `EMPTY`-объекте 90 000) |

Параметры:

- `trackId` — `songId` трека (он же `MediaItem.mediaId`);
- `streamQuality` — `AudioQuality.name()`, то есть `BASIC` \| `HIGH` \| `ULTRA`
  (подписи `128 kbps` / `192 kbps` / `320 kbps`);
- `refId` — строка контекста, приложение передаёт туда URI `MediaItem`
  (по сути «откуда играем»: id плейлиста, поиск и т.п.). Для одиночного запроса
  можно попробовать пустую строку или id плейлиста.

Подпись — как обычно: `build("GET", "/track/stream", query, &[], 0)`, но `query`
должна быть **канонической** — имена параметров дедуплицированы и отсортированы:
`refId=…&streamQuality=…&trackId=…`. Проверено: сырой порядок даёт
`INVALID_SIGNATURE`, отсортированный — `200`. См. `ALGORITHM.md` §5.4.

`refId` сервер не валидирует: проходят и `lane_likes`, и произвольная строка.

Ответ приходит `red`-шифрованным (`X-Core-Red: 1`), поэтому его надо
расшифровать `decrypt_response` — иначе вместо JSON будут бинарные байты.

Рядом в том же интерфейсе:

| Метод | Что |
|---|---|
| `GET /track/download?trackId&streamQuality` | то же, но для офлайна (стриминг тела) |
| `GET /track/effect?effect&trackId` | версия трека с эффектом |
| `GET /track/stats?trackId` | статистика трека |
| `POST /track/log?token` | лог прослушивания (токен из stats/stream) |

### Про `red`-ответы

Интерцептор `BNITInterceptor` при `X-Core-Red: 1` расшифровывает тело ответа
через `BNITManager.verifyMagic(body, X-Resp-Nonce)` и, если стоит
`X-Core-Compressed: 1`, распаковывает gzip. То есть тот же `RC4*`, что и
`field`. При `x-accept-red: 0` это не нужно.

## 5. Про `INVALID_SIGNATURE` на `/user/search/history` — разобрано

По дампу этот эндпоинт подписан ровно так:

```
GET:/user/search/history::<ts>:<nonce>::<boot_id>:<inode>
```

То есть **тем же способом, что и рабочий `/user/playlists`** — пустые `query` и
`body`. HMAC в дампе сходится, значит с алгоритмом для этого пути всё в порядке.
Причина оказалась на стороне клиента: в URL забыли поменять путь. После
исправления эндпоинт работает — это подтверждает, что офлайн-проверка по дампу
была верной.

Поэтому если `INVALID_SIGNATURE` всё же появляется, причина почти всегда в том,
что реально уходит в запросе:

1. **path отличается на байт** — лишний `/` в конце, префикс, другой регистр;
2. клиент добавляет `?` или пустой query, и на проводе получается
   `/user/search/history?` вместо `/user/search/history`;
3. в `build()` передан query, которого нет в URL (или наоборот);
4. тело непустое (тогда `field` не пуст и `flag = 1`, а подпись считалась под
   пустое тело).

Диагностика: перехватить собственный исходящий запрос (`curl -v`/mitmproxy) и
сравнить `:path` из запроса с тем, что передано в `build()` — байт в байт.

---

## 6. `x-accept-red`: на подпись не влияет

`x-accept-red: 0/1` меняет только **формат ответа** (обычный JSON против
зашифрованного «red»), в `msg1` он не входит. Поэтому подпись для `0` и `1`
одинаковая, и для снятия схем достаточно `0`.

---

## 7. Чего здесь нет

- POST/PUT/DELETE (кроме факта, что `/user/tracks` — POST, а GET даёт 405);
- точного окна `ts` (ошибка `TIMESTAMP_EXPIRED` есть, границы не измерены);
- разгадки `hints`.

Схемы ответов — в [RESPONSES.md](./RESPONSES.md). Всё выше — из дампов;
живых запросов к сервису я не отправлял.
