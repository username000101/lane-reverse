# Авторизация: как получить токен без приложения

Спецификация флоу, восстановленного из APK 1.4.7 (`LoginScreenKt`,
`LoginViewModel`, `AuthRepositoryImpl`, `LDIProvider`). Описывает, как
open-source клиент может залогиниться сам, не вытаскивая `Bearer` и `LDI`
из перехваченных запросов.

## 1. Две сущности

| Сущность | Что это | Где используется |
|---|---|---|
| **device id** (он же `LDI`) | произвольная строка, которую клиент выбирает сам | заголовок `LDI` во **всех** запросах; параметр ссылки на бота; путь опроса `/auth/<id>` |
| **token** | JWT из ответа `/auth/<id>` | `Authorization: Bearer <token>` |

Ключевой момент: **device id не проверяется вообще**. Сервер не может отличить
настоящий `Settings.Secure.ANDROID_ID` от случайной строки — он видит только
то, что прислал клиент. Приложение само это подтверждает: если система вернула
`null`, оно подставляет `lane-fallback-<время>`
(`LDIProvider`, `lp.java`).

### Проверено вживую

Логин выполнен с произвольной строкой вместо android_id (не 16 hex, не из
устройства) — сервер принял и выдал токен, аккаунт открылся штатно.

Итог: **подходит любая строка из цифр и латинских букв длиной до 60 символов**
(точнее — `A-Za-z0-9_-`, потому что таков алфавит `start`-параметра Telegram).
Никакого формата, контрольной суммы или привязки к железу нет; 16 hex — просто
то, что обычно присылает Android.

## 2. Требования к device id

| Параметр | Значение | Почему |
|---|---|---|
| длина | **≤ 60** символов | ссылка `?start=auth<id>`, Telegram режет `start` на 64 символах, префикс `auth` занимает 4. Для ASCII символы = байты |
| алфавит | `A-Za-z0-9_-` | ограничения Telegram на `start`-параметр |
| стойкость | CSPRNG | в окне логина это фактически предъявительский идентификатор |
| стабильность | хранить между запусками | токен привязан к паре «telegram-аккаунт + device id» |

Рекомендуется 32 символа из алфавита в 64 знака (`laned_bnit::random_device_id`).
Равномерность полная: `256 % 64 == 0`.

## 3. Флоу

```text
клиент                                   Telegram              сервер
  │                                         │                    │
  │ 1. id = random_device_id(32)            │                    │
  │ 2. открыть t.me/lane_music_bot?start=auth<id>                │
  │ ───────────────────────────────────────►│                    │
  │                                         │ 3. /start auth<id> │
  │                                         │ ──────────────────►│
  │                                         │                    │ 4. связать
  │                                         │                    │    telegram ↔ id
  │ 5. GET /auth/<id>  (каждые 3 с, ≤20 раз)│                    │
  │ ────────────────────────────────────────────────────────────►│
  │ ◄────────────────────────────────────────────────────────────│
  │    200 { token, isFirstAuth, user }     │                    │
  │ 6. сохранить token + id                 │                    │
```

Детали:

- запрос `/auth/<id>` **подписывается** как все остальные (тот же хост,
  `BNITInterceptor`), но **без** `Authorization` — токена ещё нет;
- `LDI` в этом запросе должен быть равен `<id>` (то же значение, что ушло боту);
- не-200 → пауза 3 с и повтор; после 20 попыток приложение сдаётся
  («Не удалось получить токен авторизации», ~60 с);
- ответ — обычный JSON, не `red`;
- `isFirstAuth = true` → сервер считает устройство новым, приложение уводит на
  онбординг (`/onboarding/artists`, `/onboarding/finish`).

## 4. Хранение на клиенте

Минимальный конфиг (так делает `laned`):

```json
{
  "deviceId": "2tIJX0-I3rg0JJy83gqhDGvF",
  "inode": "668035",
  "token": "eyJ…",
  "user": { "laneId": "…", "displayedName": "…" }
}
```

Правила:

- `deviceId` генерируется **один раз** при первом запуске и больше не меняется;
- `inode` — любое число, генерируется один раз вместе с `deviceId`. В оригинале
  берётся из `/proc/self/maps`, но значение непроверяемо: сервер достаёт его из
  расшифрованного токена, а не с устройства (проверено: `LANED_INODE=1` даёт
  корректные ответы). Хранить его в сессии нужно только ради консистентности;
- `token` перезаписывается после каждого логина; при `401` — сбросить и
  предложить войти заново (refresh-эндпоинта в APK нет);
- `user` — кэш профиля из ответа, не обязателен;
- файл — с правами `0600` (в нём bearer-токен).

Смена `deviceId` = новое устройство в аккаунте: старый токен перестаёт
соответствовать `LDI`, а на сервере появится новая запись (модель `User`
содержит `deviceIds: List<String>`). Поэтому «выйти и войти снова» лучше
делать, сохраняя `deviceId` и сбрасывая только `token`.

## 5. Безопасность

- **device id — не секрет и не аттестация.** Проверено: подходит любая строка
  из букв/цифр до 60 символов, сервер формат не валидирует. Это указатель на сессию:
  кто знает строку в момент логина, может опрашивать `/auth/<id>` и забрать
  токен, как только пользователь подтвердит вход в боте.
- Окно атаки — те самые ≤60 секунд, пока идёт опрос (и пока сервер хранит
  привязку).
- Ни Play Integrity, ни сертификатов, ни подписи устройства в клиентской части
  нет — только подпись запросов общим ключом (`BNITInterceptor`), которая
  защищает от подделки запроса, но не от чужого клиента.
- Токен — обычный bearer: кто его получил, тот и действует от имени аккаунта.

## 6. Реализация в `laned`

```powershell
laned auth-new --len 32      # сгенерировать deviceId и сохранить в laned.json
laned auth-new --id 0123456789abcdef   # или задать свой
laned auth-url               # показать ссылку на бота
laned auth-wait              # открыть бота, дождаться токена, сохранить
laned playlists              # дальше токен и LDI берутся из конфига
`

--id принимает произвольную строку — валидации нет намеренно, чтобы можно было
экспериментировать с тем, что сервер терпит. Слишком длинный id (>60) или
символы вне A-Za-z0-9_- вызывают только предупреждение: ссылка может не
открыться в Telegram, но uth-wait всё равно опросит /auth/<id>.
Приоритет источников id: --id → позиционный аргумент → deviceId из конфига.``

Переменные окружения перекрывают конфиг: `LANED_JWT`, `LANED_LDI`,
`LANED_CONFIG` (путь к файлу, по умолчанию `laned.json`).

Схема кода:

```rust
let id  = laned_bnit::random_device_id(32);        // CSPRNG, алфавит 64
let url = format!("https://t.me/lane_music_bot?start=auth{id}");
// … пользователь подтверждает в Telegram …
loop {                                             // 20 раз по 3 с
    let r = client.get(&format!("/auth/{id}"), ""); // LDI = id, без Bearer
    if let Ok(r) = r { if r.is_success() { break save(r.json()); } }
}
```

## 7. Что осталось неизвестным

- что именно бот делает на стороне сервера (в APK только клиентская часть);
- срок жизни токена и поведение после истечения (в APK нет refresh-ручки);
- строгая ли привязка токена к `deviceId` — косвенно да (`deviceIds`), но
  проверить можно только экспериментами;
- можно ли одним `deviceId` логиниться в разные telegram-аккаунты
  (вероятно, привязка перезапишется).
