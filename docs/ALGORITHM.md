# Как работает подпись Lane (`libbnit` / `BNITManager.cdrl`)

Разбор «сверху вниз»: что зачем нужно, как устроены слои и что именно проверяет
сервер. Все числа в примерах получены из рабочей реализации и совпадают с
поведением оригинальной библиотеки.

---

## 1. TL;DR

`cdrl(method, path, query, body, timestamp)` делает пять вещей:

1. Берёт **случайный nonce** (16 байт) и **текущее время**.
2. Считает от тела запроса **4-байтовый отпечаток** через RC4.
3. Подписывает `method:path:query:ts:nonce:field:boot_id:inode` ключом **HMAC-SHA256**.
4. Упаковывает подпись и поля в текстовый конверт и **шифрует** его самодельным
   RC4-подобным шифром.
5. Кодирует результат в **кастомный base64** и отдаёт три заголовка.

Сервер умеет то же самое в обратную сторону: расшифровать конверт, проверить
свежесть `ts`, пересчитать HMAC по фактическому запросу и сравнить.

---

## 2. Два уровня авторизации

| Уровень | Что доказывает | Где живёт |
|---|---|---|
| `Authorization: Bearer <JWT>` | *кто* пользователь | выдаётся сервером |
| `x-core-token` + `x-client-meta` + `x-request-trace-id` | *чем* и *когда* сделан запрос | генерируется клиентом |

JWT проверяется отдельно; три заголовка — это «подпись запроса». Без них сервер
отвечает `MISSING_SIGNATURE_TOKEN`, с неверными — `INVALID_SIGNATURE_TOKEN`,
со старыми — `TIMESTAMP_EXPIRED`.

---

## 3. Вход и выход

**Вход (5 аргументов):**

| Аргумент | Смысл |
|---|---|
| `method` | `GET`, `POST`, … |
| `path` | `/user/playlists` |
| `query` | строка запроса без `?` (может быть пустой) |
| `body` | тело запроса, `byte[]` (для GET пустое) |
| `timestamp` | смещение к текущему времени в мс; `0` = «сейчас» |

**Выход (4 элемента):**

| # | Значение |
|---|---|
| 0 | `X-Core-Token:<base64>` — основная подпись |
| 1 | `X-Request-Trace-Id:<uuid>` — идентификатор запроса |
| 2 | `X-Client-Meta:<base64>` — «метаданные клиента» (на деле 24 случайных байта) |
| 3 | `byte[]` — тот самый 4-байтовый отпечаток тела |

## 4. Общая схема

```
                        ┌──────────────┐
   method ─────────────►│              │
   path   ─────────────►│    msg1      │──► HMAC-SHA256(KEY32) ──► 32 B ──► hex(64)
   query  ─────────────►│ (через ':')  │
   ts     ─────────────►│              │
   nonce  ─────────────►│              │
   field  ─────────────►│              │
   boot_id─────────────►│              │
   inode  ─────────────►└──────────────┘
        ▲                                        │
        │                                        ▼
   now + timestamp                        ┌───────────────┐
        ▲                                 │    plain      │
        │                                 │ hex(hmac)     │
   4×u32 (urandom) ──► nonce ──► hex ────►│ | ts          │
        ▲                                 │ | nonce       │
        │                                 │ | boot_id     │
   body ──► RC4(KEY‖nonce‖ts) ──► field ─►│ | inode       │
                                          │ | flag(0/1)   │
                                          └───────┬───────┘
                                                  │
                     key2 (4 B, BE) ──────────────┤
                                                  ▼
                                   token_cipher(KEY, key2, plain)
                                                  │
                                                  ▼
                            key2 ‖ ciphertext ──► base64(custom) ──► "X-Core-Token:…"
```

## 5. По шагам

### 5.1. Случайность

15 значений `uint32` из `/dev/urandom`:

| Индексы | Назначение |
|---|---|
| 0–3 | nonce (16 байт) |
| 4 | ключ №2 шифра токена |
| 5–8 | байты UUID для trace-id |
| 9–14 | 24 байта client-meta |

Nonce, trace-id и meta пишутся **little-endian**; ключ №2 — **big-endian**
(единственное исключение).

### 5.2. Время

```text
ts = (tv_sec * 1000 + tv_usec / 1000) + timestamp
```

`timestamp` — смещение, а не абсолютное время. Поэтому `0` = «сейчас».

### 5.2.1. Откуда берётся `inode` (и почему его можно выбросить)

Оригинальная библиотека читает `/proc/self/maps`, берёт **первую** строку, где
есть и `.apk`, и `/data/app/`, и кладёт в `msg1` её пятое поле — номер inode.
Больше ничего из `maps` не используется: это одно число.

Почему это число ни на что не влияет:

- оно попадает **внутрь зашифрованного конверта** токена (`inode` — одно из
  полей после `|`). Сервер сначала расшифровывает конверт (ключ у него есть),
  достаёт оттуда `ts`, `nonce`, `boot_id`, `inode` и уже по ним пересобирает
  `msg1`. То есть значение берётся **из токена**, а не с устройства;
- сверить его с чем-то на сервере невозможно: inode — свойство файловой
  системы конкретного телефона. Никакой проверки нет, подойдёт любое число.

Нюансы, которые мы наблюдали:

- выбор строки зависит от порядка маппингов. В снятом дампе первой идёт не
  `com.skiy.lane/base.apk` (inode 192489), а GMS-сплит
  `split_CronetDynamite_installtime.apk` (inode 656421) — поэтому в примерах
  фигурирует 656421;
- значение меняется при переустановке приложения, но внутри установки стабильно.

Поэтому реализация больше не таскает снимок `maps`:

- `laned-bnit` использует константу `DEFAULT_INODE` (для воспроизводимости
  golden-вектора), а через `Options.inode` можно передать любое число;
- CLI хранит сгенерированный `inode` в конфиге рядом с `deviceId`
  (`laned auth-new` создаёт оба), переопределить можно `LANED_INODE`;
- пример формата `maps` остался в
  [`research/maps.example.txt`](../research/maps.example.txt) — синтетический,
  без данных устройства.


### 5.3. Отпечаток тела (`field`) и шифрование тела

```text
key   = KEY32 ‖ hex(nonce) ‖ ts
field = RC4*(key, body)
```

**Эти же байты — зашифрованное тело запроса.** Для POST приложение передаёт в
`cdrl` открытый JSON, получает 4-й элемент (= `field`) и отправляет его как
`body`. На проводе лежит шифртекст, и сервер считает `field` просто как сырые
байты тела — поэтому ему не нужно ничего расшифровывать для проверки подписи.
Для расшифровки и разбора JSON он использует тот же `key`.

Отсюда практическое правило: **`body` в `build()` — это открытый текст, а
отправлять нужно `out.payload`**.

`RC4*` — RC4 с одним отличием: после выдачи каждого байта в S-боксе
дополнительно мутируется одна ячейка:

```text
k = S[(S[i] + S[j]) & 0xff]
out += k ^ byte
S[(k + i) & 0xff] += k        // <-- этой строки нет в обычном RC4
```

Без неё поток совпадает с оригиналом только на очень коротких телах
(до ~15 байт), а дальше расходится — именно из-за этого подпись запросов
с непустым телом долго не сходилась.

### 5.4. Подпись

```text
msg1   = method : path : query : ts : hex(nonce) : field : boot_id : inode
digest = HMAC-SHA256(KEY32, msg1)
```

**`query` — не сырая строка, а каноническая.** `cdrl` подписывает то, что ему
передали, а Java-интерцептор (`BNITInterceptor`) передаёт результат нормализации:

```text
1) взять имена параметров из разобранного URL;
2) дедуплицировать (первое вхождение);
3) отсортировать по имени;
4) склеить как "name=value" через "&"
```

Отсюда важное следствие: порядок параметров в URL на подпись **не влияет**
(сервер нормализует так же), но подписывать надо именно отсортированную строку.
`trackId=A&refId=B&streamQuality=C` подписывается как
`refId=B&streamQuality=C&trackId=A` — иначе `INVALID_SIGNATURE`.

С одним-двумя параметрами (а также когда они уже по алфавиту) сырая строка
совпадает с канонической, поэтому ошибка долго не замечалась.

> Для `hints` и `search` остаётся нестыковка: там значение `q` приходит
> percent-encoded, и какая именно форма попадает в подпись, ещё не подтверждено.

Ключ — те же 32 байта, что и у шифра:

```
"SqperSzv" + "bntKmv_C" + "bnngeThi" + "s_12303!"   (склеено в бинаре из 4 кусков)
```

### 5.4.1. `red`-ответы

Если в ответе `X-Core-Red: 1`, тело зашифровано тем же `RC4*`, но с ключом
`KEY32 ‖ X-Resp-Nonce` (это и есть `verifyMagic`):

```text
plain = RC4*(KEY32 ‖ X-Resp-Nonce, body)
если X-Core-Compressed: 1 → ещё gunzip
```

Заголовки `Content-Length`/`Content-Encoding` после расшифровки отбрасываются,
тип принудительно `application/json; charset=utf-8`. Реализовано в
`laned_bnit::decrypt_response`.


### 5.5. Конверт

```text
plain = hex(digest) | ts | hex(nonce) | boot_id | inode | flag
```

`flag` = `"1"`, если тело непустое, иначе `"0"`.

### 5.6. Шифрование конверта

KSA (нестандартный, два ключа):

```text
S = 0..255
j = 0
for i in 0..255:
    j = (j + S[i] + KEY32[i % 32] + key2[i % 4]) & 0xff
    swap(S[i], S[j])
```

PRGA (сильно отличается от RC4):

```text
i = j = 0; carry = 0x5A
for byte in plain:
    i = (i + 1) & 0xff
    j = (j + S[i]) & 0xff
    swap(S[i], S[j])
    t     = ((S[i] + S[j]) & 0xff) ^ carry   // индекс XOR-ится с переносом
    v     = S[t] ^ byte
    v     = rotl8(v, 3)                       // поворот на 3 бита
    carry = (carry + v) & 0xff                // цепочка
    out  += carry                             // наружу идёт перенос, а не v
```

То есть это не RC4, а потоковый шифр с обратной связью по «переносу»:
каждый выходной байт зависит от всех предыдущих.

### 5.7. Сборка значения

```text
blob = key2(4 B, BE) ‖ ciphertext
x-core-token = "X-Core-Token:" + base64_custom(blob)
```

`base64_custom` — алфавит

```
zxcvbnmasdfghjklqwertyuiop1234567890-_QWERTYUIOPASDFGHJKLZXCVBNM
```

и паддинг `.` вместо `=`.

### 5.8. Остальные два заголовка

```text
x-request-trace-id = "X-Request-Trace-Id:" + UUID(4×u32 LE, формат 8-4-4-4-12)
x-client-meta      = "X-Client-Meta:" + base64(6×u32 LE = 24 байта)
```

Meta — просто случайные 24 байта, никакой структуры в них нет.

## 7. Что проверяет сервер

Модель, которая объясняет все наблюдаемые коды ошибок (это реконструкция по
структуре токена и ответам сервера, а не чтение серверного кода; точное окно
свежести и порядок проверок не измерены):

1. Достаёт значение из `x-core-token`, декодирует base64.
2. Первые 4 байта — `key2`; остальное расшифровывает `token_cipher(KEY, key2, …)`.
3. Разбивает конверт по `|`: `hex(hmac) | ts | nonce | boot_id | inode | flag`.
4. Проверяет свежесть `ts` (окно) → иначе `TIMESTAMP_EXPIRED`.
5. Считает `field = RC4(KEY‖nonce‖ts, body)` по фактическому телу запроса.
6. Собирает `msg1` из **фактических** `method/path/query`, полей из конверта и
   `field`, считает HMAC и сравнивает с `hex(hmac)` → иначе `INVALID_SIGNATURE_TOKEN`.
7. Сверяет `flag` с непустотой тела.

Отсюда следует, к чему подпись действительно привязана:

- **`method`, `path`, `query`** — потому что входят в `msg1`;
- **тело** — через `field`;
- **время** — через `ts`.

А `boot_id`, `inode`, nonce и meta сервер проверить не может — он их узнаёт
только из самого токена.

## 8. Криптопримитивы

| Примитив | Где | Замечание |
|---|---|---|
| SHA-256 | внутри HMAC | своя реализация, не OpenSSL |
| HMAC-SHA256 | подпись `msg1` | ключ 32 байта, ipad/opad `0x36`/`0x5C` |
| RC4 с мутацией S | `field` | нестандартный, см. §5.3 |
| «RC4 с переносом» | шифр конверта | кастомный KSA + PRGA |
| base64 (свой алфавит) | транспорт | паддинг `.` |

`libcrypto.so`/`libssl.so` в зависимостях есть, но **ни один символ из них не
импортируется** — вся криптография написана внутри библиотеки.

---

## 9. Чего эта схема не защищает

Это важно понимать, если смотреть на неё как на «аттестацию клиента»:

1. **Ключ лежит в клиенте.** Кто вытащил `KEY32`, может подписать что угодно —
   это обфускация, а не аутентификация клиента.
2. **`boot_id` и `inode` — самоотчёт клиента.** Сервер не знает, что было в
   `/proc/sys/kernel/random/boot_id` на устройстве, поэтому подставить любой
   UUID и любой inode можно безнаказанно. Реальной привязки к железу нет.
3. **`x-client-meta` — 24 случайных байта.** Их никто не проверяет; это шум
   (или телеметрия), а не доказательство чего-либо.
4. **Только `ts` защищает от повтора.** Пока токен свежий, его можно переслать
   ещё раз с тем же запросом — отдельного кэша nonce в схеме не видно.
5. **Границы полей не экранируются.** `msg1` склеивается через `:`; запрос
   `path="/a:b"`, `query=""` и `path="/a"`, `query="b"` дают одинаковую строку,
   а значит и одинаковую подпись. Это не ломает проверку, но позволяет
   переиспользовать подпись при другой разбивке path/query.
6. **Один ключ на HMAC и на шифр** — переиспользование ключа между примитивами.

То есть схема решает задачу «сложно подделать без реверса», а не «криптографически
доказать, что запрос сделан официальным клиентом».

---

## 10. Если портировать

Минимальный чек-лист, на чём легко ошибиться:

- `key2` — **big-endian**, всё остальное (nonce, trace, meta) — little-endian;
- base64-паддинг — `.`, алфавит начинается с `zxcvbnm…`;
- `timestamp` — **смещение**, а не абсолютное время;
- `field` в `msg1` вставляется **сырыми байтами**, а не hex;
- в конверте наоборот: `hex(hmac)` — текстом;
- флаг в конце — `1`/`0` по непустоте тела;
- PRGA: индекс `t` XOR-ится с `carry`, наружу идёт `carry`, а не `v`;
- `inode` берётся из первой строки `/proc/self/maps`, где есть и `.apk`,
  и `/data/app/` (в текущем дампе это `split_CronetDynamite_installtime.apk` →
  `656421`, а не `base.apk` приложения).

Готовые реализации: `bnit_reimpl.cpp` (C++), `rust/` (Rust, `cargo test`),
`tools/bnit_model.py` (Python, эталон для сверки с эмулятором).
